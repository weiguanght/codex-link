# 项目与会话列表不完整：数据源对比与原因分析

> 状态：**已实现后续读取改造**，见 [对话发现与历史读取](history-reading.md)。本机已放宽发现范围、增加 JSONL 兜底与完整项目索引；非桌面会话严格只读，桌面控制白名单没有放宽。
>
> **以下保留为改造前的历史分析。** 文中的“当前实现”、数量和建议均指当时快照，不代表改造后的行为。对比对象为 codex-link 原内置 codex-mobile-bridge 1.3.2 与参考项目 cc-sessions-viewer 0.5.2。

## 1. 结论

测试中“只能看到一小部分项目和会话”，**主要不是数据库没有记录，而是当前实现主动过滤掉了大量非桌面来源的会话**。

- **codex-link：数据库发现会话，JSONL 读取历史正文。**
- **参考项目：递归扫描 JSONL 发现会话，数据库补充归档、内部会话等标记。**
- 本次选中数据库共有 **1873** 条记录，其中 **1844** 条未归档；经过当前筛选，只剩 **67** 条未归档记录。
- 扫描到的 **1715** 个有效会话日志，其会话 ID **全部已存在于选中数据库**。因此，本次没有发现“日志有、该数据库完全没有”的会话。

建议先改进来源筛选和项目索引，再按需要加入 JSONL 扫描兜底，而不是直接放弃数据库。必须区分：**可以发现会话、可以阅读历史，不等于可以通过现有桌面 IPC 继续控制该会话。**

## 2. 两个项目分别从哪里读取数据

以下路径默认位于 `~/.codex/`。codex-link 的存储层使用配置的 `CODEX_HOME`；参考项目这里检查的目录函数直接使用用户主目录下的 `.codex`。本次统计针对默认目录，不包含其他用户、其他数据目录或远程主机。

| 环节 | codex-link 当前实现 | cc-sessions-viewer 0.5.2 |
| --- | --- | --- |
| 会话发现入口 | `state_*.sqlite` 的 `threads` 表 | 递归扫描 `sessions/` 下的 JSONL |
| 多个数据库的选择 | 按数据库文件修改时间，选最新文件 | 按 `state_<N>.sqlite` 的数字编号，选最大编号 |
| 日志元信息 | 主要使用数据库中的 ID、cwd、标题等字段 | 读取首行 `session_meta`，提取 ID、cwd、创建时间 |
| 来源筛选 | 严格限定桌面来源，排除子代理会话 | 没有同等桌面来源白名单；按内部会话、归档选项筛选 |
| 归档 | 根据数据库 `archived` 字段切换查询 | 数据库标记结合文件位置；启用归档选项时额外扫描 `archived_sessions/` |
| 标题 | 主要取数据库 `name` / `title` | 使用 `session_index.jsonl`，同 ID 后写入的有效标题覆盖先前标题；缺失时回退到日志解析 |
| 历史正文 | 根据数据库 `rollout_path` 读取 JSONL | 读取对应 JSONL |
| 项目列表 | 已加载会话分组；新建会话另用桌面项目配置 | 扫描日志元信息，按 `cwd` 汇总数量及最近修改时间 |
| 分页 | 默认每页 100 条，前端通过“更多”继续加载 | 先计算筛选后的总数，再分页，返回 `total` |

参考项目还会利用 Codex `thread/list` 快照补充 App 列表排名、首页标记，但**主体发现入口仍是日志扫描**，不能将它理解成单纯调用桌面会话列表接口。

### codex-link 的读取链路

```text
CODEX_HOME/state_*.sqlite → threads
    → 桌面来源 / 子代理 / 归档 / 搜索筛选
    → 项目映射、多主机合并、排序与分页
    → 网页展示已加载会话及其项目分组

打开历史：数据库记录 → rollout_path → sessions/ 或 archived_sessions/ 下的 JSONL
实时交互：现有 Codex 桌面 IPC owner
```

### 参考项目的读取链路

```text
sessions/**/*.jsonl
    + 按需扫描 archived_sessions/**/*.jsonl
    → 首行 session_meta
    + 数据库中的内部会话、归档标记
    + session_index.jsonl 标题索引
    → 按 cwd 汇总项目 / 筛选项目会话 / 计算总数 / 分页

打开历史：读取对应 JSONL
```

## 4. 已定位原因与待验证因素

### 4.1 主要原因：将“桌面来源筛选”用于历史会话发现

`SessionStore.list()` 在存在 `originator` 列时加入以下条件：

```sql
(
  originator IN (
    'Codex Desktop',
    'codex_work_desktop',
    'codex_mobile_bridge'
  )
  OR (originator IS NULL AND source = 'vscode')
)
```

此外，还根据可用字段排除 `thread_source = 'subagent'` 和 `source` 中含有字面量 `"subagent"` 的记录，并应用归档及搜索条件。

因此，来自 CLI、exec 或其他来源的历史会话，即使数据库中存在、日志可读，也可能不出现在列表里。当前策略服务于“已有桌面聊天”范围，不能直接满足“浏览全部 Codex 历史”的需求。

**不能只修改列表 SQL：** `SessionStore.get()` 同样拒绝非桌面来源和子代理记录，`history()` 又先调用 `get()`。只放宽列表会产生“看得到，点开却提示不是桌面 App 会话”的问题。

同时，来源白名单不等于实时可控制性检查；不能简单通过扩大白名单承诺所有新增会话都能发送消息。

### 4.2 项目偏少：已加载会话分组不等于完整项目索引

目前有两个不同入口：

1. **侧边栏项目分组**：`renderList()` 只对当前已加载的 `listRows` 按 `projectKey` 分组。被过滤掉或尚未分页加载的会话，不能贡献新的项目分组。
2. **新建会话的项目选择**：`AppHosts.projects()` 从桌面 `local-projects` 和已配置的远程项目生成选项，没有把 `electron-saved-workspace-roots` 或全部历史 `cwd` 作为补充来源。

已有会话的项目归属并非只认注册项目：`decorate()` 会依次尝试显式会话绑定、最长根路径匹配，最后回退到 `cwd`。因此，“没有注册为桌面项目就完全无法分组”并不准确。

参考项目值得借鉴的是：**从完整的合格会话集合建立项目索引，再在项目内分页**，而不是把当前一页会话当成全部项目目录。

### 4.3 分页是潜在问题，但不是本次 67 条的主要原因

当前默认每页 100 条，前端根据返回数量是否小于 100 来隐藏“更多”按钮。本次本地筛选后仅有 67 条，所以不是“其余 1700 多条都在下一页”。

当合格会话超过 100 条时，旧项目确实可能要继续加载才出现。后续应提供明确的 `total` / `hasMore`，并将完整项目索引与会话分页解耦。

### 4.4 数据库选择差异：需要评估，尚未证明导致本次缺失

当前项目按修改时间选库，参考项目按数字版本号选库。存在多个版本数据库时，两者可能选择不同文件。

这是兼容性审查点，**不是本次已证实的根因**。本次全部有效日志 ID 都在当前选中的数据库内。后续应结合实际 Codex 活跃数据库及可支持的 schema 制定选择策略，不能只因为参考项目不同就直接替换。

## 5. 建议改造顺序（尚未实施）

### 第一阶段：扩大历史发现范围，拆分读取和控制能力

- 保留数据库作为主要元信息来源，明确区分“全部历史”和“桌面可连接会话”等范围。
- 同步调整列表、单条元信息及历史读取入口，不再让历史浏览必须满足桌面来源白名单。
- 保留明确的归档、内部会话筛选选项；不能将所有 1844 条未归档记录直接等同于用户需要展示的普通会话。
- 单独判断历史是否可读、现有桌面 owner 是否可连接、是否允许发送或审批。前后端共同限制只读记录的写操作，并展示原因。
- 扩大发现范围仍只服务于已认证设备，不改变现有配对、认证或网络连接方案。

### 第二阶段：建立完整项目索引和可靠分页

- 基于完整的合格会话集合，结合桌面项目配置、工作区根目录和显式绑定形成项目索引。
- 保留 `cwd` / worktree 的层级差异，不按目录末尾同名强行合并项目。
- 按主机、数据目录及会话 ID 区分记录，避免本地与远程数据混淆。
- 项目计数、筛选和会话列表使用一致规则；提供 `total` / `hasMore`，项目列表不随当前加载页数变化。

### 第三阶段：加入 JSONL 兜底和索引缓存

- 数据库缺失、不可用或确实漏记录时，允许只读扫描日志首行补充发现；同一数据源内按会话 ID 去重。
- 使用 `session_index.jsonl` 补充标题，制定它与数据库标题、更新时间的冲突处理规则。
- 用文件大小、修改时间等缓存元信息，避免每次刷新解析全部历史正文。
- 对缺失日志、格式异常、数据库不兼容分别显示原因，不能静默伪装成“没有会话”。

本次日志 ID 在数据库外的数量为 0，因此**只增加扫描而保留现有来源限制，并不能解决主要问题**。

### 不直接照搬参考项目的执行模型

参考项目的聊天执行逻辑会启动自己的 `codex app-server`，使用 `thread/resume`、`turn/start` 等接口；codex-link 当前目标是控制已有桌面会话的 IPC owner。

复制日志发现方式不意味着应该一并复制会话恢复方式。自动为历史记录另起执行进程，可能引入活动 writer 冲突以及账号、模型提供方、审批上下文差异。是否支持新的执行模式，应另行设计，不能隐藏在“补全列表”的修复中。

## 6. 实施边界与验收

### 数据和工程边界

- 原始数据库、JSONL、项目配置保持只读；不要通过修改 `originator`、搬运日志或重写索引强行让记录进入列表。
- 保留正确的 SQLite WAL 读取方式。当前无 WAL 旁文件时会使用私有临时副本；不要把仍有活动 WAL 的原库标为 immutable 来规避错误。
- 参考项目的辅助数据库读取使用 `rusqlite::Connection::open`，未显式指定只读；借鉴其发现策略时，不照搬这种打开方式。
- 保留日志路径解析及目录边界校验，拒绝符号链接等造成的目录越界；不改变设备认证、同源和 CSRF 校验。
- 优先在本项目扩展层组织改造；如确需修改内置上游快照，应同步维护 `vendor/codex-mobile-bridge/UPSTREAM.json` 和完整性测试，不能静默破坏快照约束。
- 参考项目当前未成为本项目源码依赖；未来若复制其实现，应保留相应 MIT 许可证和版权声明。

### 建议验收用例

- 桌面、TUI、exec、未知来源，以及 `NULL` 搭配不同 `source` 的发现与读取行为。
- 内部会话、归档选项及“数据库已归档但文件仍在 sessions”场景。
- 超过 100 条会话、项目仅有旧会话、搜索、跨页去重和多主机汇总。
- 数据库缺失、多个 schema 文件、活动 WAL、JSONL 独有记录、重复 ID、日志缺失或损坏。
- 项目根目录、子目录、worktree、同名目录及显式绑定的分组行为。
- 日志路径越界被拒绝；历史只读记录不能通过前端或直接 API 调用自动 resume、发送消息或触发审批。
- 新增历史可见性后，原本可控制的桌面会话仍能正常发送、停止和处理审批，并完成真机回归验证。
